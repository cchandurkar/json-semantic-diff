How Array Matching Works

Naive diff tools compare JSON array elements by index. The moment an element is reordered or inserted, every subsequent record looks modified. JSON Semantic Diff infers implicit primary keys directly from empirical data evidence to pair records by identity, not position.

1. The Problem: Positional Diffing Fragility

In standard text-based and naive structural diff tools, arrays are compared index-by-index: element [0] is compared against [0], [1] against [1], and so on.

In real-world data systems—such as microservice API responses, database dumps, and sorted configuration files—record arrays are frequently reordered, paginated, or prepended. Positional diffing fails catastrophically under these ordinary operations:

The Index Shift Cascade

If an array with 1,000 records has a single new item prepended at index 0, positional matching compares record 0 with record 1, record 1 with record 2, and so on. Instead of reporting 1 insertion, the tool reports 1,000 modified records—obscuring every genuine change beneath false noise.

2. The Solution: Inferring Implicit Identity

Databases enforce primary keys so records have identity regardless of physical row order. Raw JSON documents, however, rarely specify which field is the primary key.

JSON Semantic Diff solves this by inferring identity automatically: it discovers scalar candidate fields, evaluates statistical properties across both versions, and pairs records by who they are rather than where they sit.

Candidate Discovery

  1. Leaf Path Extraction: Every scalar field present in the array's elements across either side (such as id, sku, user.email) is harvested as a single-field candidate key.
  2. Single-Field Scoring: All single-field candidates are scored against six statistical criteria.
  3. Composite Key Synthesis: If no single field achieves identity quality (score ≥ 0.90 with uniqueness ≥ 0.95 on both sides), the engine combines pairs of viable candidates (completeness ≥ 0.80, uniqueness ≥ 0.20) into 2-field composite candidates (for example, store + sku in inventory tables where neither field alone is unique).

3. The Six Scoring Signals

Every candidate key is evaluated against six independent mathematical signals that sum to a 1.0 (100%) base weight, minus small targeted penalties:

Uniqueness 26% weight

Are values distinct within each side? Measured as the average of left-side and right-side unique ratios. Duplicate values in either document immediately penalize this score.

Match Coverage 27% weight

What fraction of records in the smaller side have a matching counterpart on the other side? Measured against min(leftCount, rightCount) so appending or removing records does not erode the key's score.

Population Overlap (Jaccard) 15% weight

The Jaccard similarity of distinct key values across both sides: |A ∩ B| / |A ∪ B|. The critical safety valve preventing accidental matches between dissimilar array populations.

Completeness 16% weight

Is the candidate key present, non-null, and non-empty across every record in both arrays? Keys missing from records cannot reliably identify them.

Type Consistency 10% weight

Are key values consistently the same primitive JavaScript type (all strings, all numbers) throughout the dataset rather than mixed?

Name Hint 6% weight

A small tie-breaker bonus if the field name is identity-like (such as id, uuid, sku, code). Intentionally small (6%) so empirical data evidence always overrides naming.

Subtractive Penalties
  • Complexity Penalty (-0.03 per extra field): Applied to composite keys (e.g. store + sku has 1 extra field = -3%). Prefers a simpler single-field key when both perform equally well.
  • Volatility Penalty (-0.03): Applied if a field name suggests mutable state (timestamp, updatedAt, price, status). Kept intentionally tiny (3%) because actual value stability across datasets decides the outcome, not the field name alone.

4. The Design Lesson: Why Both Safety Signals Matter

A common trap in identity inference is relying solely on match coverage or solely on set overlap. Neither signal alone is sufficient:

Match Coverage Alone (min-based)

Measuring coverage against min(left, right) correctly forgives ordinary array growth (e.g. appending a new user). However, if used alone, comparing 3 records against 300 unrelated records where 3 happen to share keys would yield 100% coverage—a severe false positive.

Population Overlap Alone (Jaccard)

Measuring overall set overlap catches unrelated datasets. But if used alone, simply adding 5 new rows to a 10-row array drops Jaccard overlap to 66% (10/15), falsely destroying confidence in an otherwise perfect identity key.

The Dual-Signal Architecture

Match Coverage (27%) guarantees that normal record additions or removals do not break identity matching. Simultaneously, Population Overlap (15%) acts as a strict guardrail: if 3 items match out of 300 total distinct items, Jaccard overlap drops to 3 / 300 = 0.01, successfully vetoing the candidate.

5. The Decision Gates

Clearing a raw blended score is not enough. Before an inferred key is automatically applied to reorder and pair array records, it must satisfy strict safety gates:

Decision Gate Criteria Engine Action
Auto-Apply (High) Score ≥ 0.90, Margin ≥ 0.05 over 2nd best candidate, Match Coverage ≥ 0.70, and Uniqueness ≥ 0.95 on both sides. Automatically pairs array items by identity.
Medium Confidence Score ≥ 0.75, Margin ≥ 0.03, Match Coverage ≥ 0.50, and Uniqueness ≥ 0.95 on both sides. Offered to the user with visible confidence indicator.
Ambiguous Two candidates both score ≥ 0.75 and margin < 0.05. Refuses to guess; alerts user of multiple competing candidates.
Below Threshold No candidate clears the confidence gates. Safely falls back to positional index-by-index matching.
